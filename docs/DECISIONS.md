# Decisions

Every important architectural decision made so far, with the reasoning behind it.

---

## D01 — ERP is the source of truth

- **Decision**: All academic data lives in the ERP. Moodle is a downstream learning platform.
- **Reason**: Avoids dual data entry and inconsistency. Moodle is synchronized from the ERP, never the reverse.

## D02 — Modular layered architecture (API → Service → Repository → Database)

- **Decision**: Backend requests flow through API → Service → Repository → Database.
- **Reason**: Separation of concerns, testability, and the ability to swap persistence details without touching business logic.
- **Note**: Repositories and services were intentionally created as empty packages in Sprint 1; they are filled from Sprint 3 onward.

## D03 — Approved tech stack only

- **Decision**: Python 3.13+, uv, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic v2, pydantic-settings, PostgreSQL (psycopg v3), Render, Next.js.
- **Reason**: PROJECT.md prescribes the stack. No additional frameworks or libraries are introduced without explicit instruction.

## D04 — psycopg v3 as the PostgreSQL driver

- **Decision**: Use psycopg v3 with the `postgresql+psycopg://` URL scheme.
- **Reason**: Modern, actively maintained driver; first-class SQLAlchemy 2.0 support; works with Render.
- **Reason (context)**: Confirmed with the project owner before Sprint 1.

## D05 — pydantic-settings for configuration

- **Decision**: Environment variables and `.env` are loaded through pydantic-settings.
- **Reason**: Type-safe, validated settings; idiomatic FastAPI; `.env` support for local development.

## D06 — No `users` table in Sprint 2

- **Decision**: The Sprint 2 schema contains 8 tables and no `users` table, even though PROJECT.md lists `users` among database tables.
- **Reason**: Authentication is a future sprint; the login account design will be introduced with it. Students and faculty carry their own contact data.

## D07 — UUID primary keys

- **Decision**: All tables use PostgreSQL-native UUID primary keys (`uuid.uuid4`).
- **Reason**: No row enumeration, no collisions across systems, and suitable for future synchronized/distributed use.

## D08 — Uniform audit timestamps

- **Decision**: Every table has `created_at` and `updated_at` (`TIMESTAMP WITH TIME ZONE`, default `now()`; `updated_at` refreshes on update).
- **Reason**: Consistent audit trail; production-ready; confirmed to extend the earlier draft design.

## D09 — Named constraints and indexes

- **Decision**: All primary keys, foreign keys, unique constraints, check constraints, and indexes have explicit names (`pk_`, `fk_`, `uq_`, `ck_`, `ix_`).
- **Reason**: Stable, reviewable schema and predictable Alembic autogenerate diffs in future sprints.

## D10 — Check constraints over PostgreSQL enum types

- **Decision**: Status columns (e.g., attendance `Present/Absent`, sync `Success/Failed`) use `VARCHAR` with check constraints.
- **Reason**: Simpler migrations; avoids `ALTER TYPE ... ADD VALUE` complexity when allowed values change.

## D11 — `sync_logs` decoupled (no foreign keys)

- **Decision**: `sync_logs` has no FKs and stores generic `module`, `action`, `status`, `message`.
- **Reason**: The future Synchronization Engine can log events for any entity type without schema changes.

## D12 — Grades reference students/courses directly

- **Decision**: `grades` references `student_id` + `course_id` (unique per pair) with internal/external marks and a final grade.
- **Reason**: Follows the agreed database design. Retake/reexam support is noted as future work.

## D13 — Courses may exist without an instructor

- **Decision**: `courses.faculty_id` is nullable.
- **Reason**: A course can be created before a faculty member is assigned.

## D14 — Soft status flags instead of deletion

- **Decision**: `faculty.status` and `students.status` are boolean flags (default `TRUE`).
- **Reason**: Preserves academic history; records are deactivated, not deleted.

## D15 — Deterministic seed data

- **Decision**: The seed script uses a fixed random seed (`random.seed(42)`) and exact row counts.
- **Reason**: Reproducible, verifiable sample data across environments.

## D16 — Hand-written initial migration

- **Decision**: The `0001_create_core_tables` migration was authored by hand rather than autogenerated.
- **Reason**: Autogenerate requires a running database at authoring time; the hand-written migration matches the models exactly, with explicit names.

## D17 — Health endpoint only until Sprint 3

- **Decision**: The only route is `GET /health` until the Student module lands.
- **Reason**: Sprint 1 scope was foundation only; CRUD belongs to later sprints.

## D18 — Sprint-by-sprint development

- **Decision**: Only the current sprint is implemented; future-sprint code is never generated ahead of time.
- **Reason**: Follows PROJECT.md's development philosophy and keeps each sprint reviewable.

## D19 — Soft delete for students

- **Decision**: `DELETE /students/{id}` performs a soft delete by setting `students.status` to `false` (204), never a hard delete.
- **Reason**: Aligns with D14 (soft status flags). Students are referenced by enrollments, attendance, and grades; hard deletion would violate foreign keys or destroy academic history. The record remains retrievable and can be listed with `status=false`.

## D20 — Limit/offset pagination and partial updates

- **Decision**: List endpoints paginate with `limit` (1–100, default 10) and `offset` (default 0), returned via a `StudentList` envelope (`items`, `total`, `limit`, `offset`). `PUT /students/{id}` applies only provided fields (partial-update semantics).
- **Reason**: Deterministic, easy to reason about pagination; partial PUT keeps the update contract forgiving while avoiding full-object replacement.

## D21 — Tests run against a dedicated PostgreSQL database

- **Decision**: The pytest suite uses a dedicated database (`lms_erp_test`, overridable via `TEST_DATABASE_URL`), builds the schema directly from the ORM models, truncates tables between tests, and injects the test session through `app.dependency_overrides[get_db]`. The dev/seeded database is never touched by tests.
- **Reason**: PostgreSQL-only behavior (native UUID, `now()` server defaults) makes SQLite in-memory testing unreliable; a dedicated test DB keeps tests close to production while isolating them. `pytest` and `httpx` are the only new dependencies, added as dev dependencies via uv.

## D22 — Email validation without an extra dependency

- **Decision**: Student email is validated with a small regex in a Pydantic `field_validator` and normalized to lowercase, rather than using `EmailStr`.
- **Reason**: `EmailStr` requires the `email-validator` package, which was not part of the approved stack; the regex keeps the dependency footprint minimal while enforcing a valid format and case-insensitive uniqueness.

## D23 — Guarded hard delete for departments

- **Decision**: `DELETE /departments/{id}` is a hard delete but is refused with `409 Conflict` whenever the department still has faculty, students, or courses assigned (`DepartmentInUseError`).
- **Reason**: Departments have no `status` column (unlike students/faculty, which soft-delete). Because faculty, students, and courses reference `departments.department_id`, an in-use department cannot be deleted without destroying academic history. The guard returns a clean domain error instead of a raw foreign-key violation.

## D24 — Guarded hard delete for courses

- **Decision**: `DELETE /courses/{id}` is a hard delete but is refused with `409 Conflict` whenever the course still has enrollments, attendance, or grades (`CourseInUseError`).
- **Reason**: Courses have no `status` column and are referenced by enrollments, attendance, and grades (mirrors D23 for departments).

## D25 — Attendance/grades require only referencing-entity existence

- **Decision**: Creating an attendance or grade record validates only that the referenced student and course exist; it does not require the student to be enrolled in the course.
- **Reason**: The documented schema does not state that attendance/grades require an enrollment. Keeping the rule minimal matches the design and avoids inventing business requirements.

## D26 — Attendance status via `Literal`; grade marks via bounded `Decimal`

- **Decision**: Attendance `status` is enforced at the schema level with `Literal["Present", "Absent"]` (matching the DB check constraint), and grade `internal_marks`/`external_marks` are `Decimal` bounded to 0–100 with up to 2 decimal places.
- **Reason**: Uses Pydantic to reject invalid values at the boundary (422) before they reach the repository, consistent with the DB constraints. `final_grade` is validated by length only (max 5 chars) because the DB has no check constraint on it.

## D27 — Sync Logs are write-only from the integration engine

- **Decision**: The `sync_logs` table and its API are read-only from CRUD modules. Only the Sprint 7 Moodle integration engine writes via `SyncLogRepository.create` / `SyncLogService.record`.
- **Reason**: Keeps the audit trail authoritative (no arbitrary log creation) while exposing a clean read API (`GET /sync-logs`, `GET /sync-logs/{id}`) ahead of the integration work.

## D28 — Dashboard & Reports are pure read/aggregate endpoints

- **Decision**: Dashboard and report endpoints only run deterministic aggregate `COUNT`/`GROUP BY` queries over existing data; they perform no writes and hold no business mutation logic.
- **Reason**: Statistics are derived views of the ERP data; keeping them read-only avoids divergence and is consistent with the task's intent of summaries "based on the existing database".

## D29 — Moodle identity derived from ERP keys (no mapping table)

- **Decision**: Moodle users map to ERP students by `username = roll_number` and Moodle courses map to ERP courses by `shortname = course_code`; synchronization is find-or-create using these keys. No ERP→Moodle ID mapping table was added.
- **Reason**: Adding a mapping table would require a new migration, which is out of scope (schema unchanged, migration still at head `0001`). Key-based identity keeps every sync idempotent.

## D30 — Every Moodle call validated honestly; partial failure logged as `Failed`

- **Decision**: Each synchronization call validates Moodle's actual response (Moodle error payloads raise `MoodleAPIError`; e.g. `core_grades_update_grades` must return `result: true` with no failures to be `Success`). If any item in an operation fails, the operation's `sync_logs` entry is recorded as `Failed` with a per-item message (partial success is never reported as full success).
- **Reason**: Enforces the "no fake success" requirement and keeps the audit trail (`sync_logs`) trustworthy.

## D31 — Attendance sync via mod_attendance WS functions (superseded by D35)

- **Decision**: Attendance synchronization invokes `MOODLE_ATTENDANCE_WSFUNCTION` (default `mod_attendance_add_take`) with params derived from ERP attendance records.
- **Reason**: Moodle has no core Web Services function for attendance; the function belongs to the mod_attendance plugin. Making it configurable keeps the integration clean without hard-coding a plugin-specific contract, and it is still exercised with mock tests.
- **Superseded**: the configurable setting was removed once the real `mod_attendance_*` function set was installed and verified — attendance sync now calls the concrete plugin functions (see **D35**).

## D32 — Frontend: Next.js App Router, server components for reads, client components for writes

- **Decision**: The frontend uses Next.js (JavaScript + CSS Modules, App Router). Data reads happen in server components that fetch the API with `cache: "no-store"` (hence SSR/dynamic routes); CRUD forms and the delete button are client components that submit via the shared `lib/api.js` client.
- **Reason**: Keeps the frontend simple (no client-side data-fetching library — no extra dependencies beyond `next`/`react`/`react-dom`), keeps the ERP as the single source of truth, and lets every page render fresh data via the same backend contract.

## D33 — Frontend tests use Node's built-in `node:test`

- **Decision**: Frontend tests are written with Node's built-in `node:test` runner (invoked by `npm test`) and stub `global.fetch`; the project uses `"type": "module"` so `lib/api.js` imports cleanly.
- **Reason**: Exercises the API client and error handling without adding any JavaScript test framework as a dependency (respecting the "no new deps unless required" rule), and the build/start still succeeds with `"type": "module"`.

## D34 — Frontend tests are sequential and reset `global.fetch` per case

- **Decision**: Frontend API-client tests run with `{ concurrency: false }` and each case sets its own fetch stub via a shared `stubFetch(status, body)` helper rather than relying on module-level setup.
- **Reason**: `node:test` runs top-level tests concurrently and `global.fetch` is shared global state; a test that swapped the stub for its own assertions leaked state into a later test (an intermittent false failure). Making each test self-contained removed the nondeterminism found during Sprint 9 hardening.

## D35 — Attendance sync uses the concrete `mod_attendance_*` WS functions, and the integration role must hold its capabilities at the system context

- **Decision**: Attendance sync calls `mod_attendance_add_attendance`, `mod_attendance_add_session`, `mod_attendance_get_sessions`, `mod_attendance_get_session`, and `mod_attendance_update_user_status` directly (the configurable `MOODLE_ATTENDANCE_WSFUNCTION` setting was removed). The custom integration role's capabilities for this plugin are stored with `contextid = 1` (system context).
- **Reason**: Moodle's `accesslib` resolves capabilities by joining `role_capabilities.contextid` to the `{context}` table. Rows inserted with `contextid = 0` are never loaded, so `has_capability('mod/attendance:view')` stays false, Moodle marks the activity hidden, and `require_login` rejects every call with "Activity is hidden". Granting the capabilities at the system context (then purging caches) is what makes the attendance Web Services usable. Hard-coding the verified function set removes a setting that could silently point at a non-existent function.

## D36 — Bulk CSV travels as a JSON string field, not multipart form data

- **Decision**: `POST /students/bulk` accepts the raw CSV text in a JSON `csv` field (`BulkStudentImportRequest`) rather than as a multipart file upload.
- **Reason**: The backend has no `python-multipart` dependency and the stack rule forbids adding one casually. JSON keeps the endpoint testable with the existing `TestClient` and the same error contract as every other route.

## D37 — Bulk operations are preview-then-execute and idempotent

- **Decision**: `POST /enrollments/bulk/preview` is a pure dry run (200, nothing written) and `POST /enrollments/bulk` is the only writer. Both reuse the same `BulkEnrollmentRequest` body; pairs that already exist are counted as `skipped`, never duplicated. `POST /students/bulk` exposes the same shape through `dry_run: true`.
- **Reason**: Bulk writes are the highest-blast-radius operation in the ERP. A preview lets a human confirm cohort size and per-course counts before anything is created, and idempotency makes an interrupted or repeated run harmless (both for the ERP and for Moodle enrolments).

## D38 — Moodle boolean parameters are always sent as `"0"` / `"1"` strings

- **Decision**: Payload builders encode Moodle `PARAM_BOOL` values as the strings `"0"` / `"1"`, never as Python `False` / `True`.
- **Reason**: Moodle's parameter parser rejects the literal string `"False"` with `invalidparameter`, which surfaces as an opaque Web Services error. The tests assert the encoded values so a regression is caught before it reaches the live server.

## D39 — Final grades are converted to Moodle points, with the original letter kept in `str_feedback`

- **Decision**: `core_grades_update_grades` receives `rawgrade` computed from a lower-bound letter table (`A+` ≥ 90 … `F` = 0); a numeric ERP `final_grade` passes through unchanged, and the original letter is also placed in `str_feedback`.
- **Reason**: Moodle grades are numeric; the ERP stores a letter. The lower-bound table is explicit and reviewable rather than inferred. Note the current Moodle implementation discards `str_feedback` (it only forwards `userid`/`rawgrade` to `grade_update`), so the letter is not persisted — a documented Moodle limitation, not a client bug.

## D40 — Bulk enrollment auto-syncs to Moodle, and "not configured" is logged as a pending sync — not silently skipped

- **Decision**: `POST /enrollments/bulk` (and bulk student import with `sync_moodle: true`) runs the Moodle sync immediately for the ids it created. When Moodle is not configured the work is still committed and a `Failed` sync log records that the data is pending sync.
- **Reason**: The ERP is the source of truth and enrollments are not "done" until Moodle knows about them, but losing ERP data because a config var is missing would be worse. Recording an honest `Failed`/"pending sync" log keeps the audit trail truthful and gives the operator something to re-run.

## D41 — Percentages are `null` when the denominator is zero

- **Decision**: Attendance percentages (`StudentAttendanceCourse.percentage`, `StudentAttendanceSummary.percentage`, and the reports that feed them) are `null` when `total == 0`.
- **Reason**: Reporting `0%` for a student with no recorded attendance would slander them, and `100%` would be a lie. The frontend renders `—` for `null`, so the absence of data stays visibly absent.
